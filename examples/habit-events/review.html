Attach recent HABIT events to the ranker request

The request builder now reads the user's last 7 days of HABIT events through TFS v2 and passes them to the ranker as a new proto field. If that fetch fails the feed still serves, just without the signal.

The TFS v2 fetcher

RecentEvents derives a 30 ms deadline from the caller's context and wraps any TFS error. habitKeys builds one key per hour of the window (168 for 7 days). decode keeps the first 50 rows in the order TFS returned them.

The doc comment and the proto comment both promise newest first. Nothing sorts, so that is true only if TFS returns rows newest first; if it does not, the cap keeps the wrong 50.

Proto contract

A new HabitEvent message and field 12, repeated, whose comment is the contract: newest first, at most 50, empty when the fetch degrades. Field 12 is appended, never reused, so older ranker builds ignore it.

Request path: Builder.Build

The habit call runs after the Tardis fetch, sequentially, so its latency adds straight onto the feed request. Its 30 ms deadline starts when Tardis returns.

The fetcher reaches the builder through Deps, "injected by the service wiring in cmd/mfas".

Failure mode

Only the habit fetch is best-effort. Because habit_events is repeated, nil serialises as an empty list.

Storage

The habit_events table is additive; nothing in this diff reads or writes it, so its (user_id, ts DESC) index serves no query here yet.

Tests

Two new tests: the deadline fires () and decoding caps at 50 rows (). Both call newFetcher and stubTFS, which this diff does not define, so the package's tests do not compile. Nothing exercises the degrade branch in Build.

Findings and open questions

  • Missing wiring. No cmd/mfas change passes Habit; a builder made without it calls RecentEvents on a nil fetcher, which dereferences f.tfs and panics ().
  • Missing test helpers. newFetcher and stubTFS are undefined ().
  • Uncounted degradation. Errors are only logged; b.metrics goes unused.
  • Ordering. Does TFS return rows newest first? The 50-row cap depends on it ().
  • The table. What will read or write habit_events?

Parallel fetch sketch

Added after round 1 (your question on sequencing). Both calls only need the user id, so they can share an errgroup; habit stays best-effort by swallowing its own error. A proposal, not part of the diff.

g, gctx := errgroup.WithContext(ctx) g.Go(func() error { var err error; feats, err = b.tardis.Fetch(gctx, uid, baseKeys); return err }) g.Go(func() error { ev, err := b.habit.RecentEvents(gctx, uid, habitWindow) if err != nil { b.metrics.Inc("habit_degraded_total") return nil // best effort } habitEvents = ev return nil }) if err := g.Wait(); err != nil { return nil, err }
