Limit file uploads per account

Summary

Uploads now spend a token from their account’s allowance before reaching storage. Free and Pro have configured rates; an exhausted bucket produces 429 with a wait time.

Request path

The handler joins identity and enforcement. Take holds an in-memory bucket per account, and the plan configuration sets the refill rate and burst.

Suggested verdict: request changes. Team has no configured rate, and the retry client ignores the server’s wait. Both are observable paths through this diff.

Previously, the handler stored uploads immediately. Authentication already supplied account identity.

Findings

High: Team uploads bypass the limit

Team’s configuration supplies only a byte limit. Load accepts it without validation, leaving the rate at zero. Take allows every request with a non-positive rate, so Team uploads never consume tokens.

An account on that plan can send uploads continuously despite the new per-account protection. Configure Team’s rate and burst, validate every supported plan at load time, and make any unlimited policy explicit. Add a configuration-to-handler test for each plan and for an unknown plan.

Medium: retries ignore the wait

Send now retries 429 responses, but it closes the response and immediately starts the next attempt. It never reads Retry-After, which the handler sets to the next token’s wait rounded up to seconds.

When a bucket is empty, three quick attempts can all fail before it refills. That spends the client’s retry budget without giving the upload a useful chance to recover. Honour Retry-After with a bounded, cancellable wait; test a 429 followed by a successful response after the indicated delay.

Questions for the author

Is one shared allowance for every user in an account the intended product policy? Will this run in one process, or must accounts share an allowance across replicas? Should any plan deliberately allow unlimited uploads?

Uploads stores buckets in process memory without eviction. Confirm the deployment and account cardinality before treating that as a production quota.

Your questions

Sharing an allowance

Your question about account scope asks whether users compete for tokens. The bucket map uses the account id, so they do. A per-user policy would need a different key and an explicit decision about the account-wide cap.

The wait is in seconds

Your question about the header is answered by rounding the duration up. The response communicates whole seconds, so a fractional wait cannot become a zero-second retry.
